# KiKi 产品说明文档（面试版）

## 一、一句话定位

> KiKi 是一个**面向长期目标的本地自主 Agent 系统**：用户用自然语言提出目标，系统先澄清、再拆解、再自动调度本地 Claude CLI 后台执行任务，并把进度、结果、待确认事项持续回流到产品界面。

它不是聊天机器人，而是一个**“目标 → 计划 → 自主执行 → 结果回流”的完整闭环系统**。

---

## 二、当前实现了什么

### 1. 双模式输入入口
- 普通对话模式：标准 Claude 流式对话，支持中断、`--resume` 原生会话续接。
- `/goal` 长程目标模式：进入 Orchestrator 编排工作流，而非一次性出结果。

### 2. `/goal` 多阶段目标编排（核心能力）
不是一个 Prompt 模板，而是一条状态机流水线：

```
collecting_info  →  decomposing  →  generating_tasks  →  reviewing_tasks  →  presenting_plan
   多轮澄清          MECE 拆子目标       逐子目标生成任务        对齐度 Review        生成展示草案
```

特点：先信息收集（最多 3 轮），子目标按 **MECE + 逆向推演** 拆解，任务逐个子目标生成后再做一次对齐 Review，最终单独生成面向 UI 的标题/摘要/提醒策略。产出的是“可执行计划”而非“一段漂亮文本”。

### 3. 服务端自主调度与后台执行
采用 **“daemon 唯一生产者 + 浏览器只读投影”** 模型：

- 本地 daemon 循环：读 snapshot → 调度引擎判定到期任务 → 创建 `runtime_jobs` → dispatch worker 执行 → 写回 progress/result。
- 浏览器侧调度、通知、watchdog **已全部下沉到服务端 worker**（`GoalSchedulerRuntime` 被有意清空）。
- 含通知投递、超时看护（watchdog）、异常恢复（recoveryWorker）。

### 4. 服务端权威 + 前端投影的状态架构（SSOT）
- 事实源在 SQLite（`runtime_state_snapshots` + `goal_event_log` + `runtime_jobs`）。
- 写路径：命令式 API（`/api/goals/commands`）+ `Idempotency-Key` 幂等 + `baseRevision` 乐观锁（冲突 409 回灌）。
- 读路径：SSE event log 增量投影 + snapshot fallback，`BroadcastChannel` 多 Tab 同步游标。
- 前端 Zustand 仅做 projection + optimistic overlay，pending 状态严格隔离、不持久化为事实。

### 5. 结构化执行结果与多容器回流
- 多种执行产物视图：`flashcard`、`draft_review`、`confirm_action`、`reading_digest`、沙盒 WebApp 等。
- 结果同时回流到目标页、任务页、会话流、收件箱、日程五个容器。

### 6. 本地运行时基础设施
- 运行环境发现/切换/健康检查，权限模式管理。
- **干净环境变量启动**：过滤 `npm_*/TRAE_*/NEXT_*` 等污染变量，保证 CLI 会话稳定。
- 多级 JSON 容错链路（直接解析 → 平衡括号 → 格式修复 → Claude 二次修复），保障规划链路稳定。
- daemon 心跳、lease、重启快照恢复、inode 自检重连。

## 三、为什么这么做（设计动机）

| 设计决策 | 为什么 |
|---|---|
| **先澄清再规划，不一跳出结果** | 长期目标信息天然不完整，一跳式生成的“漂亮文本”无法落地执行。多轮澄清把模糊意图收敛成可执行计划。 |
| **子目标 MECE + 逆向推演 + Review** | 保证拆解不重不漏、任务与最终目标对齐，让计划具备“工程可执行性”而非“看起来合理”。 |
| **daemon 唯一生产者，浏览器只投影** | 长程任务必须脱离浏览器生命周期——关掉网页任务仍要推进。这是“长期目标”区别于“聊天”的本质要求。 |
| **服务端权威 SSOT + 命令式写入** | 避免前后端“双写”导致状态漂移；幂等键 + revision 乐观锁解决并发与多 Tab 冲突。 |
| **干净环境变量 + CLI 单入口** | 保证本地 Agent 执行的可复现性与跨环境一致性，是工程稳定性的底座。 |
| **多级 JSON 容错** | LLM 输出不可靠是常态，容错链路是规划链路能稳定上线的前提。 |
| **结果多容器回流 + 待确认机制** | 自主执行不等于失控，关键节点回到用户手里确认，形成“自主但可治理”的闭环。 |

核心理念：**把 LLM 从“对话工具”升级为“可被调度、可被治理、可持久运行的执行引擎”。**

## 四、对比 ChatGPT 的优势

| 维度 | ChatGPT | KiKi |
|---|---|---|
| **交互范式** | 一问一答，请求-响应 | 目标驱动，完整生命周期（澄清→规划→执行→回流） |
| **任务持续性** | 会话结束即终止，关闭页面任务消失 | daemon 后台常驻推进，**关掉浏览器任务继续跑** |
| **自主调度** | 无，需用户每步手动驱动 | 调度引擎按依赖/到期/优先级/并发自动派发任务 |
| **本地执行能力** | 沙箱内，受限于平台环境 | 接入本地 Claude CLI，可在用户真实工作目录读写文件、操作本地环境 |
| **状态与可恢复性** | 上下文窗口内，无持久事实源 | SQLite 事件日志 + snapshot，重启可恢复、可审计、可重放 |
| **结果形态** | 纯文本/单一回复 | 结构化产物（卡片/草稿/确认/沙盒应用）+ 多容器回流 |
| **过程治理** | 黑盒输出 | telemetry、执行时间线、待确认节点、超时看护、人工干预闭环 |
| **多目标编排** | 单线程对话 | 目标/子目标/任务/实例/日程的统一编排系统 |
| **数据归属** | 云端 | 本地优先，数据落在用户机器上 |

**一句话差异：** ChatGPT 是“你问它答”的对话助手；KiKi 是“你定目标，它持续替你推进”的**个人目标操作系统雏形**。优势集中在三点——**长程持续执行、本地真实环境操作、自主调度 + 可治理闭环**，这恰好是纯对话产品结构上做不到的。

## 五、技术栈与成熟度

- **技术栈**：Next.js 14 + TypeScript + Tailwind + Zustand；AI 运行时接入本地 Claude CLI；SQLite 持久化；本地 daemon/worker。
- **架构分层**：页面层 → 组件/投影层 → 命令/运行时 API → 服务端 services/domain/repositories → daemon/worker/SQLite。
- **当前阶段**：从高保真前端原型，跨越到“具备本地 Agent 运行时雏形的产品验证版”。已落地真实 CLI 集成、多轮编排、服务端权威状态、自动调度后台执行五大跨越。
