# 背景
- 用户想确认三件事：
  1. 当前是否每个请求都会重新启动一次 Claude CLI，能否复用原有 CLI。
  2. 为什么每个子目标至少会发生两次 Claude 往返。
  3. 先测试本机是否支持并发调用 Claude CLI，以及大致最大并发数。

# 初始假设
1. 当前聊天与目标规划都采用 `spawn()` 一次性启动 Claude CLI 子进程的模式，没有常驻 CLI worker。
2. 目标规划对每个子目标执行了“任务生成 + 任务 review”两次独立调用，因此天然至少两次往返。
3. Claude CLI 支持多进程并发调用，但吞吐会在较高并发时下降，并可能受本机资源或 CLI 账号限流影响。
4. 即使 Claude CLI 可以并发，当前代码也未利用并发，因为目标规划循环是严格串行。

# 计划
1. 阅读聊天与目标规划相关代码，确认 CLI 生命周期与会话复用边界。
2. 运行小规模并发实验，测试 `1/2/3/4/...` 路并发成功率与耗时。
3. 基于代码和实验结果回答可行性、限制与改造方向。

# 当前证据
- 聊天链路：`streamClaudeCli()` 通过 `spawn(cliPath, args, ...)` 启动一次性 Claude CLI 进程，完成后退出。
- 聊天会话续接：若存在 `claudeSessionId`，仅追加 `--resume <sessionId>`，表示复用会话上下文，不是复用同一个进程。
- 目标规划链路：`runClaudeJson()` 同样每次调用都 `spawn()` 新进程，属于一次性请求模式。
- 子目标两次往返：在目标规划循环中，每个子目标先 `generateTasksForSubGoalWithClaude()`，再 `reviewTasksWithClaude()`，因此天然至少两次 Claude 往返。

# Claude CLI 并发实验
## 实验方式
- 使用本机 `claude -p --output-format json <prompt>` 发起轻量请求。
- 记录各并发级别的总墙钟耗时、单任务耗时、成功率。

## 第一轮结果
- `1` 路：`1/1` 成功，总耗时 `9.63s`
- `2` 路：`2/2` 成功，但出现明显抖动：`4.63s` 与 `191.27s`
- `4` 路：`4/4` 成功，总耗时 `79.06s`
- `6` 路：`5/6` 成功，`1` 个任务在 `240s` 超时

## 第二轮结果
- `4` 路：`4/4` 进程均成功退出，总墙钟 `30.38s`
- `5` 路：`5/5` 进程均成功退出，总墙钟 `37.86s`
- 说明：CLI 在 `4-5` 路并发下可运行，但响应时间抖动较大；`6` 路已出现不稳定

# 初步结论
1. 当前实现没有常驻 Claude CLI worker，所有请求均为“一次 spawn，一次退出”。
2. 聊天的 `--resume` 只解决上下文连续性，不解决进程复用与冷启动成本。
3. 当前机器上保守稳定并发建议从 `4` 路开始；`5` 路可进一步验证；`6` 路已观测到超时，不建议直接作为默认值。
