# 任务执行过程说明

## 这份文档说明什么

本文用面向用户的方式解释一次任务是如何被 KiKi 执行的，包括：

- 输入给 Agent 的 prompt 包含什么。
- Agent 被期望输出什么。
- Agent run 是如何启动、运行、解析和验收的。
- 任务什么时候会完成，什么时候会等待用户确认或补充信息。
- 以“5天详细行程规划”任务为例，还原一次实际执行过程。

这里的“任务执行 Agent”不是普通聊天助手。它的输出不是直接展示给用户看的最终聊天消息，而是先交给系统解析，再由系统决定任务卡片、状态、确认面板、日志、归档和后续续跑。

## 总体链路

一次任务执行可以理解为 9 个阶段：

1. 用户触发任务。
2. 系统创建任务运行实例。
3. 系统生成任务执行 prompt。
4. 任务进入后台队列。
5. Worker 领取任务并启动 Agent run。
6. Agent 按 prompt 执行任务并返回结果。
7. 系统解析 Agent 输出。
8. 系统校验和验收结果。
9. 系统写回任务状态，决定完成、等待用户、失败或继续修复。

## 第 1 步：用户触发任务

用户在目标详情、会话卡片或任务列表中点击执行某个任务。

系统收到的关键输入包括：

- 目标信息：例如“越南胡志明市5天游玩规划”。
- 子目标信息：例如“行程攻略规划”。
- 任务信息：例如“5天详细行程规划”。
- 任务实例信息：本次运行的独立实例 ID、日期标签、运行介绍等。
- Runtime 环境：使用本地 Claude CLI、工作目录、权限模式等。

这一阶段的要求：

- 参数必须完整。
- 当前任务必须绑定到一个会话或目标上下文。
- 必须能创建隔离的任务工作区。
- 如果同一个实例已经在排队、运行或等待用户，不重复创建新运行。

## 第 2 步：创建任务运行实例

系统会为这一次执行准备一个独立的运行环境。

这一步会做几件事：

- 创建或确认会话级 workspace。
- 创建任务级 workspace。
- 把本次任务实例标记为已启动。
- 生成 requestId，用来追踪这次执行。
- 把任务实例和 runtime job 关联起来。

这样做的目的：

- 同一个任务可以有多次执行实例。
- 每次执行都有独立日志、轨迹、结果和 workspace。
- 后续可以恢复、取消、追踪或归档某一次具体运行。

## 第 3 步：生成任务执行 prompt

系统会把任务上下文整理成一份给 Agent 的完整 prompt。

这份 prompt 的核心目标是告诉 Agent：

- 你不是普通聊天助手。
- 你是后台任务执行 Agent。
- 你的职责不是解释过程，而是交付可验收产物。
- 最终回复必须是一个完整 JSON 对象。

prompt 主要包含以下内容。

### 任务身份

Agent 会被告知：

- 当前目标是什么。
- 当前子目标是什么。
- 当前任务标题是什么。
- 当前任务描述是什么。
- 当前任务执行目标是什么。
- 建议工作目录是什么。
- 当前任务依赖哪些前置任务。

### 交付物契约

交付物契约定义“这件任务到底怎样才算完成”。

它通常包含：

- 预期结果。
- 核心交付物。
- 结果类型。
- 主格式。
- 展示形式。
- 可导出格式。
- 必须包含的结构化 blocks。
- 完成标准。

例如“5天详细行程规划”的交付物契约是：

- 需要交付完整的 5 天游程表。
- 每天要有上午、下午、晚间三个时段。
- 要包含景点游览、用餐建议、交通方式和预计花费。
- 核心景点要纳入。
- 时间分配要合理。

### 协作契约

协作契约定义 Agent 和用户怎么分工。

它通常包含：

- 协作模式。
- Agent 负责什么。
- 用户负责什么。
- 用户是否需要确认、作答、补充信息或线下操作。
- 用户介入发生在执行前、执行中还是 Agent 输出后。
- 完成归属是 Agent、用户还是双方。

协作契约决定任务什么时候可以直接完成，什么时候必须等用户参与。

### 第一步：执行前提自检

Agent 必须先判断任务是否具备执行前提。

规则大致是：

- 如果任务需要用户在执行前提供信息，Agent 必须检查这些信息是否已经具备。
- 如果缺失用户才能提供的关键信息，Agent 不能继续猜测执行，必须返回等待用户的结构化结果。
- 如果任务是 Agent 自主完成，只有遇到无法靠检索、推理或执行补齐的硬缺口，才等待用户。
- 如果用户介入时机是“Agent 输出后确认”，Agent 应先产出候选方案或结果，再在结构化字段中声明需要用户确认。
- 如果这是恢复执行，已经由用户回答过的问题不能再次重复提问。

### 最终回复格式

Agent 的最终回复必须满足硬性格式：

- 只能输出一个完整 JSON 对象。
- 不要输出 Markdown 代码块。
- 不要在 JSON 前后输出自然语言解释、执行过程或思考过程。
- 可以在 workspace 写文件作为副本，但最终回复仍必须把完整 JSON 输出到消息中。
- 如果需要用户确认，也必须按等待用户模板输出完整 JSON，并设置 `awaiting_user=true`。

这条要求非常重要，因为系统后续不是靠人读，而是靠程序解析。

### 输出模板 A：正常完成

如果任务完成，Agent 应输出一个 JSON 对象，核心字段包括：

```json
{
  "summary": "本轮执行结果摘要",
  "final_message": "面向用户的一段自然语言总结",
  "result_view_kind": "generic_result",
  "awaiting_user": false,
  "awaiting_reason": "",
  "interaction_requirement": {
    "type": "none",
    "timing": "not_required",
    "reason": "",
    "question": "",
    "options": [],
    "suggested_actions": [],
    "should_notify_user": false
  },
  "suggested_actions": [],
  "artifacts": [],
  "task_result": {
    "schemaVersion": 1,
    "taskId": "当前任务 ID",
    "instanceId": "当前实例 ID",
    "title": "结构化产物标题",
    "status": "done",
    "blocks": []
  },
  "deliverable_check": {
    "matched": true,
    "confidence": "high",
    "delivered_artifacts": [],
    "missing_deliverables": [],
    "criteria_results": [],
    "gap_reason": ""
  },
  "structured_output": {}
}
```

这里最关键的是：

- `awaiting_user=false` 表示不需要用户继续参与。
- `task_result.blocks` 是真正展示给用户的主产物。
- `deliverable_check.matched=true` 表示 Agent 自己声明交付物满足任务标准。

### 输出模板 B：等待用户

如果任务需要用户确认、作答或补充信息，Agent 应输出一个 JSON 对象，核心字段包括：

```json
{
  "summary": "需要用户补充关键信息后才能继续",
  "final_message": "请用户补充本轮全部缺失信息，并说明原因。",
  "awaiting_user": true,
  "awaiting_reason": "缺少用户才能提供的关键输入",
  "interaction_requirement": {
    "type": "provide_context",
    "timing": "before_execution",
    "reason": "缺少用户输入，暂时无法完成主交付物",
    "question": "请一次性列出本轮所有缺失字段。",
    "options": ["候选项1", "候选项2", "候选项3"],
    "suggested_actions": [],
    "should_notify_user": true
  },
  "artifacts": [],
  "task_result": {
    "status": "pending_user",
    "blocks": []
  },
  "deliverable_check": {
    "matched": false,
    "missing_deliverables": ["缺失项1"]
  }
}
```

这里最关键的是：

- `awaiting_user=true` 表示系统要暂停任务并显示用户参与面板。
- `interaction_requirement.type` 必须准确区分用户参与类型。
- `options` 必须是具体答案，不是“补充信息”这种动作描述。
- `deliverable_check.matched=false` 表示当前还不能算完成。

## 第 4 步：任务进入后台队列

prompt 生成后，系统不会直接在前端同步执行任务，而是创建一个 runtime job。

runtime job 的初始状态通常是：

- `queued`：已排队，等待后台 Worker 领取。

runtime job 会保存：

- 目标、子目标、任务和实例。
- runtime 环境。
- workspace 路径。
- requestId。
- 当前状态。
- 后续执行进度、日志、轨迹、结果、阻塞点等。

这样做的原因：

- 任务可能很久，不适合同步阻塞前端。
- Worker 可以独立运行。
- 页面刷新后仍能恢复状态。
- 任务可以取消、续租、恢复或归档。

## 第 5 步：Worker 领取任务

后台 Worker 会周期性扫描排队任务。

当 Worker 领取任务时，会做以下事情：

- 把 job 从 `queued` 改成 `running`。
- 写入 lease owner。
- 写入 lease 过期时间。
- 启动租约续租定时器。
- 准备 AbortController，用于取消或租约失效时中断 Agent。
- 调用任务执行入口开始真正执行。

这里的 lease 机制用于保证：

- 同一个任务不会被多个 Worker 同时执行。
- 如果 Worker 卡住或退出，租约过期后任务可以重新排队。
- 用户取消任务时，可以清理租约，让 Worker 在续租时中断。

## 第 6 步：执行前信息充分性检查

进入任务执行后，系统会先做一次信息充分性检查。

这一步不是最终 Agent run，而是系统先判断任务有没有明显缺失用户信息。

可能结果有两种：

### 信息不足

如果缺少用户才能提供的信息，例如：

- 出发城市。
- 预算上限。
- 账号授权。
- 个人偏好。
- 必须由用户选择的目标。

系统会直接生成等待用户的结果：

- 任务状态变为等待用户。
- 显示需要用户补充的信息。
- 生成候选项。
- 不启动主 Agent 去猜测执行。

### 信息足够

如果信息足够，系统进入下一步，正式调用 Agent。

## 第 7 步：启动 Agent run

系统通过 Claude CLI 启动 Agent run。

传给 Agent 的内容就是前面生成的任务执行 prompt。

运行时要求：

- Agent 在隔离任务 workspace 中工作。
- Agent 可以根据权限模式调用工具。
- 工具调用会被记录到执行轨迹。
- Agent 最终必须返回一个完整 JSON 对象。

Agent run 期间系统会监听这些事件：

- Agent 开始运行。
- Agent 输出增量文本。
- Agent 调用工具。
- Agent 返回最终消息。
- Agent 报错。
- Agent 完成。

系统会持续记录：

- 当前阶段。
- 用户可见进度。
- 工具调用轨迹。
- Agent 最终输出片段。

## 第 8 步：解析 Agent 输出

Agent 返回最终消息后，系统会尝试把它解析成任务结果对象。

理想情况是 Agent 返回纯 JSON：

```json
{
  "summary": "任务完成",
  "awaiting_user": false,
  "task_result": {
    "blocks": []
  },
  "deliverable_check": {
    "matched": true
  }
}
```

如果返回的是自然语言，系统就无法稳定知道：

- 任务是否完成。
- 是否需要用户参与。
- 用户参与类型是什么。
- 应展示哪个结果卡片。
- 是否满足交付物契约。
- 是否要归档到已完成。

所以系统必须尽量把 Agent 输出变成结构化结果。

## 第 9 步：本地结构校验

解析后，系统会先做本地结构校验。

本地校验关注的是“格式和结构是否可用”，例如：

- 是否能解析出 JSON。
- 是否包含 `task_result`。
- `task_result.blocks` 是否存在。
- block 类型是否合法。
- 必填字段是否存在。
- `awaiting_user` 和 `interaction_requirement` 是否一致。
- `deliverable_check` 是否结构正确。

如果本地校验失败，系统会尝试让 Agent 修复结构。

修复要求通常是：

- 不重新做任务。
- 不重新规划。
- 把刚才输出修正成合法 JSON。
- 补齐缺失字段。
- 修复 block schema。

如果多次修复仍失败，任务会被标记为未完成或等待 Agent 补齐。

## 第 10 步：非 JSON 确认内容兜底

如果 Agent 没有返回合法 JSON，但系统识别到它像是在要求用户确认，例如包含：

- 用户确认。
- 请用户确认。
- 等待用户。
- 确认选择。
- 候选方案。
- 推荐方案。

系统会尝试把这段自然语言兜底转换成等待用户的结构化结果。

这是一种容错机制，目的是避免任务完全失败。

但它有风险：

- 自然语言含义可能被猜错。
- `confirm` 可能被误判成 `provide_context`。
- 已经确认过的信息可能再次被提问。

刚刚的问题就发生在这个区域。

## 第 11 步：验收员检查

当结构合法且不是等待用户时，系统会进入验收阶段。

验收员关注的是“内容是否真的满足任务要求”，例如：

- 是否覆盖预期结果。
- 是否满足完成标准。
- 是否只是泛泛总结。
- 是否缺少关键交付物。
- `deliverable_check.matched=true` 是否可信。

验收可能给出几种结果：

- 通过：任务可以完成。
- 需要修复：Agent 需要补齐内容。
- 需要用户：缺少用户才能提供的信息。
- 失败：无法达到完成标准。

如果验收要求修复，系统会让 Agent 做语义补齐。

语义补齐和重新执行不同：

- 它应基于已有结果补差。
- 不应重新规划整个任务。
- 不应重复已经做过的工具调用。
- 修复后还要重新本地校验和验收。

## 第 12 步：写回任务状态

任务最终会写回一种状态。

### 完成

如果结果通过解析、校验和验收：

- job 状态变为 `completed`。
- 任务实例归档到已完成。
- 保存结果、日志、轨迹。
- 前端展示最终 `task_result.blocks`。

### 等待用户

如果结果需要用户参与：

- job 状态变为 `awaiting_user`。
- 生成 blocker。
- 保存 resume token。
- 前端展示确认、作答或补充信息面板。

用户提交后，系统会带着用户提交内容恢复执行。

### 失败

如果执行异常、结构修复失败或验收失败：

- job 状态变为 `failed`。
- 保存错误信息。
- 前端展示失败原因。

### 取消

如果用户手动停止任务：

- job 状态变为 `cancelled`。
- 清理 lease。
- Worker 在续租时中断当前 Agent run。

## 第 13 步：用户确认或补充后的续跑

当任务处于等待用户状态时，用户提交确认或补充信息。

系统会做以下事情：

- 校验 resume token。
- 把当前 blocker 标记为已解决。
- 保存用户提交内容。
- 把 `awaiting_user` 清掉。
- 把用户提交写入 resume context。
- 将任务重新放回队列。

恢复执行时，Agent prompt 会额外包含：

- 用户对上一次阻塞点的决定。
- 用户反馈内容。
- 前序工具调用。
- 前序 Agent 输出。
- 禁止重新规划、禁止重复提问、禁止重复工具调用的要求。

恢复执行的核心原则是：

- 只做增量续跑。
- 已由用户回答的问题不能再问。
- 前序产出必须沿用。
- 只补齐缺口。

## 以“5天详细行程规划”为例

下面用刚刚的任务还原一次实际执行过程。

### 任务输入

目标：

- 越南胡志明市5天游玩规划。

目标摘要：

- 双人5天胡志明市深度游。
- 人均预算 3000 元。
- 已拆解为证件签证、交通预订、住宿安排、行程攻略、预算管理、物资准备、现场执行等子目标。

子目标：

- 行程攻略规划。

任务：

- 5天详细行程规划。

任务描述：

- 基于景点调研和美食推荐，规划 5 天详细行程。
- 每天分为上午、下午、晚间三个时段。
- 合理安排景点游览顺序、用餐地点及交通衔接。
- 确保行程节奏合理、体力分配均衡。

预期交付物：

- 完整的 5 天游程表。
- 含每日时段安排、景点游览、用餐建议、交通方式及预计花费。

完成标准：

- 5 天游程表完整。
- 每天含上午、下午、晚间安排。
- 核心景点已纳入。
- 时间分配合理。

协作契约：

- 协作模式：Agent 先产出结果，用户再确认。
- Agent 负责：规划行程框架、安排景点顺序、匹配用餐建议、计算预算。
- 用户负责：确认行程节奏是否符合偏好，提出调整建议或特殊需求。
- 用户介入类型：确认。
- 用户介入时机：Agent 输出后。
- 完成定义：用户确认行程表无异议，或根据用户反馈调整至满意。

### 预期的 Agent 输出

这个任务理想情况下应该返回两种结果之一。

如果系统认为“用户确认后才算最终完成”，Agent 应返回等待确认的 JSON：

```json
{
  "summary": "已生成5天详细行程，等待用户确认",
  "final_message": "已完成胡志明市5天详细行程规划，请确认行程节奏是否符合预期。",
  "awaiting_user": true,
  "awaiting_reason": "需要用户确认行程安排",
  "interaction_requirement": {
    "type": "confirm",
    "timing": "after_agent_output",
    "reason": "协作契约要求用户确认行程节奏与安排",
    "question": "请确认以上5天行程安排是否符合你的预期？",
    "options": ["确认行程，按此执行", "整体节奏放慢一点", "替换或增加景点"],
    "suggested_actions": [],
    "should_notify_user": true
  },
  "task_result": {
    "status": "pending_user",
    "blocks": [
      {
        "kind": "heading",
        "text": "胡志明市5天详细行程规划",
        "level": 1
      }
    ]
  },
  "deliverable_check": {
    "matched": false,
    "missing_deliverables": ["用户确认行程安排"]
  }
}
```

如果系统认为“Agent 已完成交付，用户确认只是后续动作”，Agent 应返回完成 JSON：

```json
{
  "summary": "已完成胡志明市5天详细行程规划",
  "final_message": "已为你规划好双人5天胡志明市深度游行程。",
  "awaiting_user": false,
  "interaction_requirement": {
    "type": "none",
    "timing": "not_required",
    "reason": "",
    "should_notify_user": false
  },
  "task_result": {
    "status": "done",
    "blocks": [
      {
        "kind": "heading",
        "text": "胡志明市5天详细行程规划",
        "level": 1
      }
    ]
  },
  "deliverable_check": {
    "matched": true,
    "missing_deliverables": []
  }
}
```

无论是哪种，都必须是纯 JSON，不能在 JSON 前后加自然语言。

### 实际第 1 次执行

系统创建任务实例后，把任务放入队列。

Worker 领取任务，启动 Agent。

Agent 收到的 prompt 中已经写明：

- 你是后台任务执行 Agent。
- 任务是“5天详细行程规划”。
- 需要交付完整 5 天游程表。
- 协作契约是 Agent 输出后用户确认。
- 最终只能输出一个完整 JSON 对象。

但 Agent 实际返回的是：

```text
我需要先检查依赖任务提供的景点调研和美食推荐信息。根据执行前提自检，协作模式为 agent_with_user_confirmation，用户介入时机为 after_agent_output，符合规则C。我应先产出完整行程方案，再请求用户确认。基于目标摘要中已明确的"双人5天胡志明市深度游，人均预算3000元"及胡志明市核心景点和美食常识，我可以产出主交付物。
```

这段内容的问题是：

- 它不是 JSON。
- 它像过程说明，而不是结构化任务结果。
- 它没有 `task_result`。
- 它没有 `deliverable_check`。
- 它没有明确可解析的 `interaction_requirement`。

所以系统无法稳定判断任务状态。

### 第 1 次失败后的兜底

系统发现 Agent 输出不是合法 JSON。

但这段自然语言里出现了类似“用户确认”“候选方案/分析内容”的语义。

系统触发兜底逻辑：

- 把非 JSON 输出转换成一个等待用户的结构化结果。
- 显示为需要用户确认或补充。
- 创建 blocker。
- 任务进入等待用户状态。

这一步的设计目标是避免任务完全失败。

但当时存在一个问题：

- 本来应该识别为 `confirm`。
- 兜底后又被后续逻辑误转成了 `provide_context`。

这就是后续重复确认的第一层原因。

### 用户第一次确认

用户选择了：

```text
体验优先方案（更舒适）
```

系统记录提交：

- 用户已确认。
- 用户选择为“体验优先方案（更舒适）”。
- blocker 标记为 resolved。
- 任务重新入队。
- resume context 写入用户选择。

恢复上下文类似：

```text
用户对上一次阻塞点的决定：确认继续
用户反馈：用户确认选择：体验优先方案（更舒适）
```

恢复执行时，Agent 理论上必须：

- 吸收“体验优先方案”。
- 继续完成行程规划。
- 不再重复问“是否确认行程安排”。
- 不重新规划整个任务。
- 不重复已经做过的工具调用。

### 实际第 2 次执行

Agent 续跑后返回了这样的内容开头：

```text
根据恢复执行模式和用户已确认的"体验优先方案"，我将直接产出完整的5天行程规划交付物。

{"summary":"已完成胡志明市5天深度游详细行程规划，按体验优先、舒适节奏安排核心景点与美食", ...}
```

这次比第一次更接近正确，因为后面有 JSON。

但它仍然有两个问题：

- JSON 前面多了一段自然语言。
- JSON 里面又设置了 `awaiting_user=true`，要求用户再次确认。

所以系统再次进入等待用户状态。

### 实际第 3 次执行

后来 Agent 返回了更接近合法的 JSON：

```json
{
  "summary": "已完成胡志明市5天深度游详细行程规划，按体验优先、舒适节奏安排核心景点与美食",
  "awaiting_user": true,
  "awaiting_reason": "等待用户确认行程安排",
  "interaction_requirement": {
    "type": "confirm",
    "timing": "after_agent_output",
    "question": "请确认以上5天行程安排是否符合你的预期？"
  }
}
```

这次格式基本对了，但语义仍然不对。

因为用户已经确认过“体验优先方案”，恢复执行后不应该再问同类确认问题。

### 这次问题的根因总结

这次不是单点问题，而是多层问题叠加：

- 第一次 Agent 没遵守最终 JSON 输出协议。
- 系统用兜底逻辑尝试从自然语言里恢复任务状态。
- 兜底逻辑把确认场景误转成了补充信息场景。
- 用户确认后，续跑上下文虽然带上了用户选择，但 Agent 又按协作契约机械地产生新的确认点。
- 运行时状态写回曾经被中途状态影响，导致最终结果没有按预期完成归档。

### 修复后预期流程

修复后，这类任务应按下面方式运行：

1. Agent 首次输出必须是纯 JSON。
2. 如果任务需要用户确认，`interaction_requirement.type` 应保持为 `confirm`。
3. 用户确认后，系统把确认内容写入恢复上下文。
4. 恢复执行时，Agent 必须吸收已确认内容。
5. 如果 Agent 又返回同类确认，系统会识别为重复确认并自动吸收，不再打断用户。
6. 最终任务应进入完成或继续交付状态，而不是重复出现确认面板。

## 为什么一定要 JSON

JSON 是任务执行协议，不是为了让用户阅读。

它让系统可以明确判断：

- 任务是否完成。
- 是否需要用户。
- 用户需要做什么。
- 展示什么结果。
- 交付物是否满足标准。
- 是否要归档。
- 是否要续跑。
- 是否要创建 blocker。

如果 Agent 只返回自然语言，系统只能猜。

这次重复确认问题本质上就是：

- Agent 输出不符合协议。
- 系统尝试猜测。
- 猜测链路出现偏差。

所以长期正确方向是：

- Agent 输出必须结构化。
- 非 JSON 输出要先强制修复成 JSON。
- 只有修复失败时才进入兜底。
- 兜底逻辑也必须严格区分 `confirm`、`provide_context`、`answer` 等不同用户参与类型。

## 用户视角下的状态变化

用户看到的任务状态大致对应后台状态：

- 待执行：任务还没进入运行。
- 执行中：任务已排队或 Worker 正在运行。
- 待确认：Agent 已产出结果，需要用户确认。
- 待补充：缺少用户才能提供的信息。
- 已完成：任务通过解析、校验和验收，结果已归档。
- 已取消：用户停止任务，后台已释放租约。
- 失败：Agent 执行、结构解析或验收失败。

## 一句话总结

一次任务执行的核心不是“Agent 说了什么”，而是“Agent 是否按任务协议返回了可解析、可验收、可驱动状态机的结构化结果”。

刚刚的行程任务失败点在于：

- 第一次 Agent 返回的是过程说明，不是 JSON。
- 后续系统为了容错做了自然语言兜底。
- 兜底和续跑处理不够严格，导致用户已经确认过的信息又被重复确认。
