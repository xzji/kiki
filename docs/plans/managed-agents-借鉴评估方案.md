# KiKi 对照 Managed Agents 的演进方案（评估版）

> 参照 Anthropic 工程博客《Scaling Managed Agents: Decoupling the brain from the hands》（2026-04-08）。
> 本文目的：用产品经理能看懂的语言，讲清楚 **当前 KiKi 有哪些问题、哪些建议改、哪些先不改、为什么**。
> 本文不动代码，只做评估与建议。

---

## 0. 一句话背景

Anthropic 的核心观点可以浓缩成一句：

> 一个长期运行的 Agent，应该把"脑（推理）/ 手（执行）/ 记忆（会话）"拆成三个独立的零件，而不是塞在一个容器里。
> 这样模型变强了，整个系统不用重写；某个零件挂了，其他零件还能继续跑。

KiKi 当前架构的方向其实是一致的，但还处在"半解耦"的中间状态。下面把当前问题逐个翻译成产品语言。

---

## 1. 当前到底有哪些问题

按"用户能感受到的程度"从高到低排：

### 问题 1：浏览器关掉，目标就停了 🔴 用户能感受到

**现象**
用户起了一个长期目标，KiKi 自动派发任务在后台跑。但目前的"调度大脑"一部分在浏览器里。一旦用户关掉网页或电脑休眠：
- 新任务不再被自动派发
- 已经在跑的任务勉强能跑完，但下一个任务不会自己接上
- 早上回来打开浏览器，目标进度可能停在昨天

**技术翻译**
浏览器侧有一个 `GoalSchedulerRuntime`，服务端 daemon 也有一套 `goalSchedulerEngine`，两边并存，浏览器是事实上的"主调度器"。原文的术语叫"adopted a pet"：一个不能丢的、必须人工照顾的脆弱角色。

**用户体感**
"明明是自动 Agent，为什么我关电脑就不动了？"

---

### 问题 2：刷新页面，对话/进度有时会"回到一个不对的状态" 🟡 偶发但难解释

**现象**
- 任务进度在前端 store、后端 snapshot、SQLite 里都各存一份
- 网络抖动或两边时序错开时，刷新后会看到比真实进度旧的状态
- 没有"回放"能力，无法看到"这个任务过去 1 小时到底做了什么"

**技术翻译**
当前是"快照覆盖"模式：服务端定期把当前状态拍一张照片同步给前端，旧的事件丢了。原文推荐的是"事件流（append-only log）"模式：所有发生过的事都记下来，前端只是基于事件流计算出当前视图。

**用户体感**
"这个任务好像跑过又没跑过？" "怎么进度倒退了？"

---

### 问题 3：模型变聪明了，但 KiKi 给它的"拐杖"还在 🟡 看不见但持续吃成本

**现象**
KiKi 内部为目标规划写了大量"模型可能输出坏 JSON"的兜底：
- 直接解析 → 失败 → 平衡括号截取 → 失败 → 字符替换修复 → 失败 → 让 Claude 自己再修一次

`/goal` 流程也写死了 5 个阶段（澄清 → 拆解 → 生成任务 → Review → 出方案）。

**问题在哪**
原文里 Anthropic 自己讲了一个例子：他们曾经为 Sonnet 4.5 写过"上下文焦虑"重置逻辑，结果换 Opus 4.5 完全没这个毛病，那段代码立刻变成"死重量"。
KiKi 现在的 JSON 多级修复、5 阶段 workflow，都属于这一类——**它编码的是"模型现在做不到什么"，而不是"产品要什么"**。模型一升级，这部分代码就有可能成为反向负担。

**用户体感**
短期没感受，但长期会让"产品迭代"和"模型迭代"互相打架。

---

### 问题 4：执行器只支持本地一种"手" 🟡 限制未来形态

**现象**
所有任务都假定运行在"用户本机的 Claude CLI"。其他可能的执行环境暂时没法插：
- 远端容器
- 用户公司内网的服务
- 手机端
- MCP 工具

**技术翻译**
项目已经抽出了 `Runner` 接口（一个统一的"执行器"形状），方向是对的；但 Runner 的入参里仍然带着 KiKi 的业务对象（goal、task、instance 这些），所以新增一种"手"还是要懂 KiKi 业务，而不是只懂"接收一个输入、返回一个结果"。

**用户体感**
现在用户感受不到，但只要 KiKi 想接"远程执行""共享 Agent""手机端代办"，今天的 Runner 就需要改。

---

### 问题 5：凭据和执行环境绑在一起 🟠 安全隐患

**现象**
任务执行时，Claude CLI 的环境变量里会包含 API token 等凭据。本地单机使用风险可控，但只要未来：
- 让 Claude 跑用户提供的脚本
- 接 MCP 工具调外部 SaaS
- 在共享/远程环境跑任务

那么"模型生成的代码可以读到凭据"就会变成真实风险。原文里 Anthropic 把这个问题专门列出来，给出的修复方式是：**凭据放金库，不进入 Claude 的执行沙箱**。

**用户体感**
今天感受不到，但是属于"一旦出事就不可挽回"的那一类问题。

---

### 问题 6：会话状态有两套，互相牵制 🟢 工程感受得到

**现象**
- KiKi 自己有一份 `trajectory.json`（自己的执行轨迹）
- 同时又依赖 Claude CLI 的原生 sessionId（用 `--resume` 续接）

两套 session 共存，意味着想换底层模型/CLI 时，要同时改两个地方。原文的主张很明确：session 是系统的财产，不应被任何一个具体 brain 私有。

**用户体感**
没有直接感受，但会拖慢"换底层模型""支持其他 LLM"的效率。

---

## 2. 改与不改的建议矩阵

按"价值 vs 成本"分四档。

| 优先级 | 问题 | 建议 | 价值 | 成本 |
|---|---|---|---|---|
| P0 必须改 | 1. 浏览器关掉就停 | 把调度器搬到 daemon，浏览器只看不调 | 高（直接影响产品定位） | 中 |
| P1 建议改 | 2. 状态对不上、无法回放 | 把 trajectory 升级成统一事件流，snapshot 退化为派生视图 | 高 | 中偏高 |
| P1 建议改 | 4. Runner 入参太"业务化" | 把 Runner 接口收窄成"输入 + 输出"，业务转换放 adapter 层 | 中高（解锁未来形态） | 低中 |
| P2 留意 | 5. 凭据和执行同环境 | 单机阶段先不动，但要在文档里标记"扩展前必须改" | 高（一旦扩展就必须） | 中 |
| P3 暂不改 | 3. 模型拐杖（JSON 修复 / 5 阶段 workflow） | 不删，但加灰度开关，按模型版本验证哪些可以下线 | 中 | 低 |
| P3 暂不改 | 6. 双 session 并存 | 短期保留 Claude CLI `--resume`，等问题 2 完成后自然解耦 | 中 | 中 |

## 3. 三件最该做的事（产品经理可以直接拿去排期）

### ✅ 第一件：把"调度大脑"从浏览器搬到 daemon

**给 PM 的话术**
> 现在 KiKi 的"自动派发任务"逻辑还有一部分跑在浏览器里。我们要把它整体搬到 daemon（用户开机就在跑的后台进程），让浏览器只负责显示，不负责决策。

**用户能感受到的变化**
- 关掉网页，目标继续推进
- 重启电脑，daemon 自启动后接着跑
- 即使浏览器从来没打开，今晚的任务也会按时被派发

**衡量是否成功**
- 关闭浏览器 12 小时后，目标推进步数 ≥ 应推进的 95%
- 用户首次进入网页的"看到第一条最新进度"时间 < 1 秒（接近原文的 TTFT 改进）

**改动量**
中等。daemon、worker、SQLite 这些底座已经有了，是"把现有零件接好"，不是"从零造"。

---

### ✅ 第二件：把执行轨迹做成"事件流"

**给 PM 的话术**
> 现在我们存"任务最新状态"，但没存"任务过去发生了什么"。一旦出问题，无法回放。我们要改成"所有事情都记一笔流水账，当前状态随时算出来"，就像银行流水和余额的关系。

**用户能感受到的变化**
- 任务详情页可以"回放过去 1 小时这个任务做了什么"
- 状态再不会"莫名其妙倒退"
- 客服/排查问题时，可以拿到完整时间线

**衡量是否成功**
- 任意任务可调用"事件回放"，时间精度到秒
- 刷新前后状态完全一致的会话占比 ≥ 99%

**改动量**
中偏高。需要把现在三个文件（progress / result / trajectory）合并成统一日志，并把前端从"读快照"改为"读日志"。建议做成 2-3 个 sprint 的渐进迁移。

---

### ✅ 第三件：把 Runner 接口"去业务化"

**给 PM 的话术**
> 现在新增一种执行方式（远程容器 / 手机端 / 第三方工具）需要懂 KiKi 业务模型。我们要让"执行器"这一层只关心"接到什么输入、返回什么输出"，业务转换放在外面一层。

**用户能感受到的变化**
- 短期：感受不到
- 长期：KiKi 可以接更多种执行环境，比如"让 Claude 在我公司的服务器上跑""调用 MCP 工具"

**衡量是否成功**
- 新增一种 Runner 实现的工作量 < 1 天
- 业务对象和执行接口在代码上完全分离

**改动量**
低中。属于一次性整理，做完就解锁未来很多事。

---

## 4. 建议先不改的事

### ⏸ 不改：JSON 多级修复 / `/goal` 5 阶段 workflow

**理由**
这部分确实是"为模型当下缺陷写的拐杖"，但：
1. 当前模型版本（Sonnet/Opus 4.5）下，它**有效**，移除会立刻掉成功率
2. 删除收益是"代码更干净"，对用户体验提升有限
3. 一旦换模型，可以快速验证是否还需要

**建议做法**
不要删除，但要做两件事：
- 在每条"修复路径"上加日志埋点：触发频率多少、命中率多少
- 在隐藏调参里加开关：可以一键关掉某条修复路径，按模型版本灰度

这样未来某天模型升级，可以**用数据决定哪些拐杖可以扔**，而不是凭感觉删。

---

### ⏸ 不改：本地单机的凭据策略

**理由**
KiKi 现阶段定位是"用户本机自用"，凭据和执行同在一个机器，相当于用户自己电脑上跑自己的脚本，风险可控。

**建议做法**
不动代码，但在以下三个文档里**显式写一条警示**：
- `PROJECT_OVERVIEW.md` 安全章节
- `claudeEnv.ts` 顶部注释
- 未来"远程执行/共享 Agent"立项文档

警示内容：
> 一旦 KiKi 扩展到非用户本机执行（远程容器 / 多用户共享 / 第三方工具调用），必须先做凭据沙箱隔离，否则 Claude 生成的代码可以直接读到 token。

---

### ⏸ 不改：Claude CLI 原生 session（`--resume`）

**理由**
- 这是当前对话连续性的基础设施，移除风险大
- 第二件事（事件流）做完之后，这层会自然变成可选项

**建议做法**
等"事件流"上线、KiKi 自己的 session 真正成为唯一真理来源后，再讨论是否要去掉 Claude CLI 的 session 依赖。**不要先删后建**。

---

## 5. 三件事的推荐顺序

```
第一件：调度搬到 daemon  →  立刻解决"关浏览器就停"的产品观感问题
       ↓
第二件：执行轨迹事件流  →  顺势把"前后端状态打架"问题一并解决
       ↓
第三件：Runner 去业务化  →  在前两件稳定后做，为未来形态铺路
```

每一件做完都是产品上**用户能讲出来的进步**，而不是只有工程师知道的"代码更好了"。

---

## 6. 如果只能做一件，做哪件？

**做第一件：把调度器搬到 daemon。**

理由：
- 它是**用户能直接感受到**的差距
- 它是**KiKi 产品定位**（"长期目标自动推进"）的必要条件
- 项目已经有 daemon 和 worker，**不是从零造**，是把已有零件接到位
- 它是后两件事的基础——大脑不在浏览器里之后，事件流和 Runner 改造才能真正发挥价值

---

## 7. 给老板/管理层的一句话总结

> KiKi 现在的架构方向和 Anthropic Managed Agents 的设计哲学一致，差距主要在于"还没把大脑彻底搬出浏览器""执行历史还没做成可回放的流水账""执行接口还没和业务彻底解耦"。建议按"调度下沉 → 事件流 → 接口净化"三步走，每一步都对应一个用户能感知的产品改进；同时把"模型拐杖"和"凭据隔离"这两块标记为观察项，不立刻动。
